# Agent registry & bounded orchestration

**Router:** `apps/api/app/routers/agents.py`  
**Audience:** Admins/engineers author and publish agents; any role can start a run if permitted by policy.

## Purpose

Version agent instructions, bind models and tools, publish reviewed versions, start bounded agent runs (Temporal-backed, ≤12 tool calls), and view the evaluation-based promotion scorecard. The seeded registry includes Planner, Metadata, SQL Analyst, Pipeline, Quality, Troubleshooter, Policy, and Analytics; administrators can enable, disable, edit, version, and publish these definitions.

## Binding tools: two registries, one bounded call budget

An agent version binds to tools from two separate registries, both validated at save time and both spent against the same 12-call bounded-run budget during a run:

- `tool_names` — the internal `ToolDefinition` registry (built-in Python handlers or allowlisted HTTP; see [`tools.md`](./tools.md)). Global, not project-scoped.
- `query_tool_names` — the governed, project-scoped `QueryTool` registry: SQL tools with business metadata (purpose, data source, line of business, owner) generated by the wizard, verified via `/query-tools/{id}/test`, and published (see [`query_tools.md`](./query_tools.md)). Only **published** query tools in the agent's current project validate; unpublished or cross-project names are rejected on `POST /agents` and `POST /agents/{id}/versions`.

`GET /agents/{agent_id}` resolves both bindings and returns them as `tools` and `query_tools` alongside the raw name lists.

The `Policy` agent is configurable for explanation and policy evidence, but it cannot override deterministic enforcement. Risk keywords, project scoping, tool risk levels, required approvals, and write/execute restrictions are evaluated in code before execution. The `Analytics` agent is a read-oriented preset for catalog grounding, profiling, SQL generation/preview, and lineage context; it is still governed by the same tool contracts and approval gates.

**Execution:** `temporal_activities._execute_bound_tools()` (used by both the Temporal-backed path and the local fallback in `run_agent_plan_locally`) executes bound `ToolDefinition` tools and bound `QueryTool`s in the same loop, per plan step, sharing the ≤12-call budget. A bound query tool is only invoked if it is published in the run's project, does not require approval, and its parameter contract can be satisfied conservatively (same "never guess a required parameter" policy as the internal tool loop). Query tool execution reuses `connector_runtime.execute_connector_query` / `staging.execute_parameterized_read_only` — the same functions the external gateway uses — so a SQL tool an internal agent invokes gets identical PII masking, read-only enforcement, and governance logging to one invoked by an external accessor over `/external/v1` or `/mcp`.

This closes a gap where SQL tools generated, verified, and published through the query-tool wizard had no path into agent execution: an agent could only ever call internal `ToolDefinition` tools, never the governed SQL registry external accessors already used.
