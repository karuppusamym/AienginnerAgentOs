## 8. Agent/tool harness — improvement assessment (this session)

Read `temporal_activities.py`'s `_execute_agent_plan()`/`_execute_bound_tools()` and `tool_runtime.py`'s `execute_tool()` directly (not the docs) to answer "anything need to improve over there." Findings, all confirmed against code:

| Area | Finding |
| --- | --- |
| Plan generation | Real when a non-`local_mock` provider is configured: the model is prompted with grounding context and must return 3–6 steps from the enabled, registry-configured agent set (with `Planner` and `Policy` retained as control-plane participants); it falls back to a deterministic plan on parse/validation failure. |
| Tool parameter construction | **Two-tier, both guarded.** Tier 1, `_parameters_for_tool()`: fills only grounded objective/query values, exact project-scoped UUIDs, known catalog relations, bounded limits, and declared defaults — no model call. Tier 2, `_llm_parameters_for_tool()` (new this session): only reached when tier 1 can't ground every required field, and only when a real (non-`local_mock`) provider is configured. The model gets one narrow, schema-only prompt; its output must pass the exact same `validate_parameters()` every other call is checked against, *and* any field shaped like a foreign key (`asset_id`, `file_id`, `mapping_id`, `rule_id`, `schedule_id`, `job_id`) must resolve to a real row scoped to the run's project or the whole fill is discarded — a well-formed but hallucinated id is rejected exactly like a missing one. Every model attempt is logged to `ModelCallLog` (`purpose="agent_tool_parameter_fill"`) whether accepted or rejected, and accepted evidence is tagged `parameter_source: "heuristic"` or `"model"` so a run stays explainable after the fact. Covered by `test_llm_parameter_fill_is_guarded_and_grounded`, which asserts both the acceptance path (grounded id, `dataset.profile` runs) and the rejection path (hallucinated id, tool is skipped, nothing executes). |
| Policy authority | **Implemented.** The configurable `Policy` agent can explain policy evidence, but deterministic approval keywords, project scope, risk level, and write/execute boundaries remain authoritative. A generated plan crossing a deterministic boundary is paused for approval before bound tools run. |
| Agent coverage | **Expanded.** Seeded registry now includes configurable `Policy` and `Analytics` agents in addition to Planner, Metadata, SQL Analyst, Pipeline, Quality, and Troubleshooter. All ten built-in tools have published contracts; agents can be versioned, enabled/disabled, and bound to internal tools or governed query tools. |
| Failure handling | A `ToolRuntimeError` on one tool logs a warning and moves to the next planned step. There's no reflection/replan step that feeds the failure back to the model and tries a different tool or adjusted parameters within the same run. |
| Run budget | A flat 12-tool-call ceiling per run, no per-step or per-tool-type budgeting, no cost/token accounting surfaced per run beyond the raw call count. |
| Model provider resilience | One provider is selected once per run; a planning failure falls back to the fixed deterministic plan, not a retry against a secondary configured provider. |
| Self-evaluation | No automated LLM-as-judge or benchmark scoring of a completed run beyond the existing `GET /agents/{id}/scorecard` (which scores evaluation-suite pass rate, not live-run quality). Historical benchmark dashboard / ablation testing were already flagged as not built in `ARCHITECTURE_DECISIONS.md` §2 — still true. |

The remaining harness gaps are reflection/replan after a failed call, per-tool cost/token accounting (beyond the per-attempt `ModelCallLog` rows the parameter-fill tier now writes), provider failover, and automated live-run quality judging.
